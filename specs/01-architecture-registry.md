# 01 — Architecture registry

**Status:** done
**Depends on:** —

An architecture describes, once, what an invocation needs for one model family:
the checkpoint slots, the flag each fills, the recommended defaults, what the
family is for and which runner loads it. It names no file; models fill its slots.

## What it does

- The Models page's **Architectures** tab lists every architecture with search and
  tag filters, a **New Architecture** form and a card per architecture.
- A card shows the slots (name, flag, family), default parameters, tags, Civitai base
  models, and expands each slot into the models registered in its family with an
  **Add Model** form pre-filled with that family. LoRAs of the architecture sit in
  a folded section of the card ([`09`](09-lora-management.md)).
- Built-ins are seeded from the reference file on every start and cannot be
  edited or deleted; user-created architectures can.
- Tags drive the list filters and the project workspace's picker: `image`,
  `video`, `edit`, `audio`, `llm`, `upscale` are offered as one-click adds, and
  any other word typed is accepted.

## Shape

`Architecture` in `shared/src/drift/shared/Api.scala`:

```
id, label, tool: SdCpp | LlamaCpp, checkpoints: List[CheckpointRef],
defaultParameters: Map[flag, value], civitaiBaseModels, tags, builtIn,
pixelDiffusionDecoder (its configurations upscale rather than generate),
promptingNotes: Option[String] (how the model reads a prompt, for the assistant),
assistantTemplateId: Option[String] (the assistant system template a project
targeting it starts with — 32; none is drift's helper),
sizeMultiple: Int (the multiple every side is aligned up to — 27)
```

`CheckpointRef(name, familyId, flag, required)`.

- CRUD at `/api/architectures`, generated by `RouteHelpers` with
  `canDelete = !builtIn`.
- Storage: `~/.config/drift/architectures/<id>.json`.
- Reference: `backend/resources/reference/architectures.json`, 27 built-ins
  (image: `flux.2-dev`, `flux.2-klein-9B`, `flux.2-klein-4B`, `z-image-turbo`,
  `krea2`, `qwen-image`, `qwen-image-2.1` (tagged edit too — one checkpoint
  generates and edits), `ideogram-4`, `mage-flow-turbo`, `sensenova-u1.5`,
  `boogu-image`, `ernie-image`, `hidream-o1`;
  edit: `mage-flow-edit-turbo`, `boogu-image-edit`; video: `wan-2.2-14B`, `wan-2.2-5B`, `ltx-2.3`, `ltx-2.5`,
  `minimax-h3`, `hunyuanvideo-1.5`; upscale: `pid-flux2`, `pid-flux2-2048`, `pid-flux1`,
  `pid-qwen-image`; llm: `qwen3.6-35b-a3b`, `gemma-4-26b-a4b`).
- Seeding: `StorageService.seedFromResource` rewrites every built-in from the
  reference (so a fixed flag reaches existing configs), leaves alone a user
  entity that happens to hold a reference id, and deletes a built-in the
  reference no longer lists.
- **A record is written only when it differs.** Each stored file's bytes are
  compared with the bytes the reference item serialises to — `save` and the
  seed share one `serialize` so they cannot drift — and an identical one is
  left alone. A start where nothing changed therefore writes nothing, with no
  marker file recording what was seeded: the files *are* that record, so there
  is no second source of truth to go stale, and a file corrupted or edited by
  hand is repaired rather than trusted (François, 2026-09-20). A reference file
  that reads as empty or undecodable seeds **nothing** and retires nothing,
  rather than reading as "no built-ins exist" and deleting them all.
- It decides who owns an id by reading each stored file's `id` and `builtIn` as
  raw JSON (`storedOwnership`), never through the entity's codec: the records
  on disk are the previous build's, and a field added since would make every
  one of them "fail to decode" on the very start that rewrites them — the rule
  migrations already follow ([`38`](38-entity-migrations.md)).
- UI: `frontend/src/drift/frontend/pages/architectures/` (`ArchitecturesPage`,
  `ArchitectureCard`, `ArchitectureForm`, `ModelForm`, `LoraSection`).
- `ArchitectureTags` (shared) holds the suggested vocabulary and `derive`, used
  once at start to tag user architectures that predate the field.

## Notes

- `defaultParameters` holds only what is intrinsic to the family: geometry, steps,
  schedule, `--diffusion-fa`, `--cache-mode`, `--mmap`. Machine and build concerns
  belong to the runtime layer ([`16`](16-parameter-resolution.md)); a checkpoint's
  own numbers belong to the model.
- `familyId` is free text on both sides of the join. A typo yields an empty
  model list with no error.
- `sizeMultiple` is declared, not asked for: sd-cpp aligns a request up to
  `vae_scale_factor × diffusion_model_down_factor` and answers with the bigger
  image without being asked, and nothing on the wire says what that product is.
  Six built-ins are 32 — Qwen Image 2.1, SenseNova U1.5, both LTX, MiniMax-H3
  and Wan 2.2 5B — and the other twenty-one 16.
- **It has no default.** Every record carries its own: the reference file
  writes one on all 27 built-ins and the form asks for it, starting at 16 — the
  number nearly every family wants — as a control's starting position, not a
  fallback. A default in the case class would have meant the next family whose
  number is not 16 inheriting one that is, silently, which is the failure this
  field exists to stop (François, 2026-09-20). Records written before the field
  took no migration: they were all built-in, and seeding rewrites those.
- Tags are declared, never inferred at runtime: a model says what it is, and an
  unforeseen kind of model needs a word, not a schema change.
- An empty parameter value means a bare flag.
- The `RuntimeTool` and other singleton enums encode as plain strings; their
  codecs are built with `withDiscriminatorFieldName(None)`.
